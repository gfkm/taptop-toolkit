# Разработка Taptop Toolkit

Это изолированная экспериментальная поставка. Менять файлы разрешено только внутри этой папки, если пользователь отдельно не разрешил другое.
Соседние design-system/, html-export/, taptop-export/ и taptop-helper — действующий пользовательский MVP; не редактировать их и не подключать как runtime dependencies.
Прочитай README.md, system/docs/project-layout.md и system/docs/architecture.md. Для работы над сайтом достаточно скила, `next` и `doctor`. Рабочие заметки сопровождающих (`system/docs/handoffs/`, `system/docs/superpowers/`) есть только в их рабочей копии и в поставку не входят; `system/docs/implementation-plan.md` — исторический документ.
Перед работой с проектом запусти `npm run toolkit -- projects`. Если проектов несколько и пользователь не назвал нужный, уточни выбор; никогда не используй общий «активный проект» или соседний проект вместо отсутствующего. Для изменения передавай путь к проекту явно (`--project projects/<папка>`). Текущая схема папок, реестр артефактов и каталог результатов описаны в `system/docs/project-layout.md`; состояние проекта проверяет `npm run toolkit -- doctor --project projects/<папка>`.
Для работы над сайтом пользователя (Figma, AI-дизайн, HTML/CSS, сборка, поиск результатов, диагностика) прочитай скил `system/skills/taptop-site-transfer/SKILL.md` и следуй ему; при расхождении этот файл важнее.
Клиентские значения запрещено встраивать в ядро. Примеры и тесты — отдельные синтетические фикстуры.
Перед завершением запусти npm test. Не объявляй живой импорт проверенным по результатам unit tests.
Не публикуй пакет до определения лицензии и проверки происхождения. Git-индекс родительского проекта содержит чужую незавершённую работу — не коммить его целиком.

## Скил и документация обновляются вместе с системой

- Источники правды для агентов: скил `system/skills/taptop-site-transfer/` (порядок работы), этот `AGENTS.md` (правила), `system/lib/cli-usage.js` (команды). Копии скила для Claude Code (`.claude/skills/`) и Codex (`.agents/skills/`), `CLAUDE.md` и `system/docs/cli-reference.md` генерирует `npm run docs:sync`; вручную их не править.
- Любое изменение поведения — команда, код ошибки, шаг `next`, путь, формат `kit.json`, правило сборки — в той же правке обновляет скил, его справки и `system/docs/troubleshooting.md`; затем `npm run docs:sync` и `npm test`.
- `npm test` падает, если копии скила устарели, команда CLI не описана в скиле, код ошибки не объяснён в troubleshooting, действие `next` не объяснено в `SKILL.md`, ссылка битая или `metadata.toolkit-version` скила не равна версии в `package.json`. При повышении версии Toolkit скил перечитывается целиком, правится и только потом получает новую версию.
- Урок живого переноса записывается туда, где его прочтёт следующий агент: факт Taptop — в `system/docs/html-normalizer.md`, урок извлечения — в `system/docs/figma-extraction.md`, изменение порядка работы — в скил.
- В Claude Code копии обновляются сами: хук `.claude/settings.json` после правки скила, `AGENTS.md` или `cli-usage.js` запускает `system/scripts/agent-docs-hook.js`. В других клиентах — `npm run docs:sync` вручную; `npm test` всё равно поймает забытую синхронизацию.
- `system/test/getting-started.test.js` дословно исполняет все команды `system/docs/getting-started.md` на свежей копии поставки: изменил поведение — обнови руководство.
- Смысл текста тесты не проверяют. Изменив поведение, перечитай и поправь: `README.md`, `system/docs/project-layout.md`, `system/docs/troubleshooting.md`, `system/docs/html-normalizer.md` (таблицы правил и фактов), `system/docs/getting-started.md`, `SKILL.md` и затронутые `references/`.
- Пользователь получает обновлённый скил вместе с новой версией Toolkit: он лежит внутри поставки, отдельная установка не нужна.

## Агентная работа и UI skills

Правила маршрутизации и компактные роли находятся в `system/docs/agent-operating-model.md` и `system/agents/`. По умолчанию работает один агент; специалист подключается только по явному триггеру и передаёт короткий handoff с артефактом и доказательством.

Локальные skills `frontend-design`, `apple-design`, `emil-design-eng` и `improve-animations` применяются только при проектировании или проверке UI расширения и AI-generated дизайна. Они не входят в исходники Toolkit, клиентские проекты и публичную поставку.

Для UI-задачи расширения работайте в отдельном проекте импортёра и прочитайте его `docs/extension-ui/DESIGN.md`, затем нужные части `anatomy.md`, `inventory.md` и `decisions.md`. Полный playbook в `system/docs/references/` (только в рабочей копии сопровождающих) — справочник; не добавляйте React, Tailwind, Storybook или shadcn runtime в vanilla-расширение без явного согласия пользователя.

## Входящий HTML/CSS

Любая присланная пользователем HTML-страница проходит через нормализатор. Основной путь — зарегистрировать её как артефакт и собрать: `npm run toolkit -- artifact add …`, затем `npm run toolkit -- build --project … --artifact pages/<имя>`; сборка сама вызывает нормализатор. Прежняя одностраничная команда `npm run toolkit -- normalize …` остаётся для старых проектов. Вручную приводить чужой HTML к профилю компилятора запрещено. Правила, коды отчёта и границы — `system/docs/html-normalizer.md`.

- Исходные файлы пользователя не менять: они лежат в `input/<имя>/`. Результат нормализации управляемой сборки — `.taptop/work/<артефакт>/` и копия в `output/html/<артефакт>--<сборка>/` вместе с `normalization-report.json`; у прежней команды — `source/normalized/`.
- Ничего не терять молча: правило становится классом Taptop, уходит дословно в Embed-стили или блокирует сборку ошибкой.
- Интерактив (аккордеон) — редактируемые слои плюс сгенерированный Embed в `Scripts`; JavaScript из исходника не копировать.
- Перед импортом сравнить оригинал и результат `system/docs/tools/normalize-compare.html` на 1440/992/768/480/320 (ширины холстов Taptop) и 900/700/375: `npm run toolkit -- serve` и ссылка `links.compare` из вывода `build`. Сравнение считается только с `taptop-preview.css`, который эмулирует базовые классы слоёв Taptop. Цель — ноль расхождений; «0 elements matched» — это проваленное сравнение, а не успех. Результат записать: `npm run toolkit -- check … --level local`.
- Новый случай, которого нормализатор не знает, — сначала тест с синтетической фикстурой, потом правило в `system/lib/html-normalizer.js` и строка в `system/docs/html-normalizer.md`.

## Неподвижный каркас UI Kit

**Визуальный эталон** — Monochrome UI Kit (Claude Design): сайдбар 260px,
заголовок 52/800, карточки и панели с радиусом 10px и рамкой gray-150,
моно-подписи JetBrains Mono, на ≤991px — верхняя панель с бургером и
выезжающим меню. Любой кит проекта выглядит так же; меняются только шрифт,
значения и набор разделов по данным проекта.

**Кит не верстается вручную.** Он собирается генератором из данных проекта:

```sh
npm run toolkit -- ui-kit projects/<папка> --data design-system/kit.json
npm run toolkit -- build --project projects/<папка> --artifact ui-kit
```

`design-system/kit.json` — шрифт, цвета, роли типографики, радиусы, тени и компоненты (ряды
элементов с классами проекта); `roles.css` рядом — CSS ролей проекта (`type-*`,
`btn*` с состояниями) дословно. После изменения данных кит перегенерируется
`ui-kit … --replace`: генератор заменяет только свои неизменённые файлы и
откладывает прежние в `.taptop/history/ui-kit/`. Старые проекты без
`layoutVersion` собирают кит прежними командами `normalize` и `compile`. Оболочку (`kit-*`) правит только генератор в
`system/lib/ui-kit/`; агент не дописывает и не переопределяет её стили в проекте.
Мобильное меню кита подключается автоматически (поведение `menu`). Синтетическая проверка сборки проектного кита — `system/test-support/synthetic-kit-and-page.js`.

Для каждого проекта используется один и тот же каркас UI Kit Toolkit. Канонический
каркас, его структура витрины и базовые имена классов находятся в
`system/examples/ui-kit-default/source/` и создаются через `system/lib/ui-kit/`. Он не является
готовым дизайном клиента: это пустая, предсказуемая оболочка для проектных
значений и вариантов.

- UI Kit из Figma, экран без UI Kit, AI-направление и присланный HTML/CSS — это
  **источники доказанных значений**, а не повод собрать вторую дизайн-систему.
- Агент обязан сначала назвать используемый каркас и затем заполнить в нём
  только подтверждённые foundations, варианты компонентов и контентные
  примеры. Нельзя заново придумывать каталог, навигацию витрины, соглашения об
  именах или параллельный набор классов.
- Значения, состояния или компоненты, которых нет в источнике, остаются
  `MISSING`; их нельзя маскировать значениями из демо-кита или другого проекта.
- Расширить сам каркас, изменить его базовые классы или заменить его другим
  шаблоном может только UI Kit Architect после явного решения пользователя и
  с планом миграции. Это не часть обычного Figma/HTML/AI-импорта.

Передать работу дальше можно только с записью: путь к каркасу, перечень
заполненных проектных значений, перечень `MISSING` и проверка, что созданные
классы ссылаются на существующие роли каркаса либо имеют отдельное
доказательство из источника. Витрина, сделанная с нуля по скриншоту, не
считается UI Kit Toolkit и не может быть принята как готовая.

## Жёсткое правило: страница обязана переиспользовать UI Kit

После импорта UI Kit любая страница **обязана применять его точные классы** для
повторяющихся ролей: типографики, кнопок, ссылок и вариантов компонентов. Нельзя
создавать их аналоги вроде `body`, `display`, `button`, `button--yellow` и затем
надеяться, что импортёр «догадается» о соответствии. Такие имена не являются
ролями каркаса и могут совпасть с системными классами редактора.

Перед выдачей JSON агент обязан проверить, что классы страницы с ролями UI Kit
содержатся в `syncPackage.classes` с теми же именами и теми же правилами, что в
импортированном UI Kit. В предпросмотре импорта они должны числиться «уже есть»
или «без изменений», а не «новые». Если правила различаются, сначала обновляется
сам UI Kit, затем страница; режим «Обновить» для чужого/системного одноимённого
класса использовать запрещено. Необъяснимое совпадение с `body`, `html`, `root`
или похожим общим именем — ошибка сборки, а не переиспользование.

Управляемая сборка проверяет это сама: страницу регистрируют с
`--depends ui-kit` и первым стилем `design-system/roles.css`; общий класс
получает один ключ проекта `<namespace>/class/<имя>`. `build` отказывает с
`UI_KIT_CLASS_MISMATCH` (правила отличаются от текущего кита),
`CLASS_RULE_CONFLICT` (два артефакта расходятся) и `RESERVED_CLASS_NAME`
(системные имена Taptop из `system/lib/taptop-system-classes.js`: классы слоёв
`div`, `text`, `button`, `text-button`, `link-block`, `image`, `image__img`,
`svg-icon`, `svg-icon__path`, `html`, `body`, `head`, `root` и все имена базовой
таблицы стилей Taptop из `system/lib/taptop-base-classes.json` — `section`,
`container`, `link`, `badge`, `menu__*`, `slider__*`, `pop-up__*`, `tabs__*`, `is-active` …). В присланном HTML
нормализатор сам переименует такой класс в `u-<имя>` (`RESERVED_CLASS_RENAMED`);
в ките и страницах используй то же имя `u-<имя>`.
Имя с окончанием `-0`, `-1` или числом с нулём впереди (`col-1`, `step-01`) Taptop
считает счётчиком дублей и сохраняет под другим именем: нормализатор переименует
его в `col_1` (`CLASS_COUNTER_RENAMED`), а `build` и `ui-kit --check` откажут с
`CLASS_NAME_RESPELLED`.
Предупреждение `NO_UI_KIT_ROLES_USED` означает, что страница не использует ни
одной роли кита — проверь, не созданы ли аналоги. Аналог с другим именем
(`button` вместо `btn`) автоматически не распознаётся: это остаётся
обязанностью агента.

## Каждая найденная ошибка становится правилом

Toolkit должен улучшаться с каждым переносом. Агент, который нашёл расхождение
между ожидаемым и живым результатом в Taptop (вёрстка, адаптив, импорт,
сохранение), не имеет права ограничиться ручной правкой проекта или JSON.
Обязательный порядок:

1. **Причина, а не симптом.** Найти механизм в редакторе (стили, ключи,
   сериализация) и подтвердить его живым чтением или минимальной пробой.
   Догадка без проверки в правила не вносится.
2. **Тест.** Синтетическая фикстура, воспроизводящая случай, в `system/test/` или
   в отдельном проекте импортёра `test/`. Клиентские значения в тесты не копировать.
3. **Исправление в генераторе.** Нормализатор, компилятор или импортёр — так,
   чтобы следующий перенос не повторил ошибку. Ручная правка выходного JSON или
   живого проекта допустима только как дополнительная починка уже
   импортированного.
4. **Запись факта.** Строка в таблице «Taptop facts the rules rely on» в
   `system/docs/html-normalizer.md`: что верно в Taptop, дата и как проверено, какое
   правило на это опирается. Для нового правила нормализатора — строка в
   таблице преобразований с кодом отчёта.
5. **Локальная проверка должна ловить это заранее.** Если ошибка была видна
   только в живом Taptop, расширить эмуляцию (`taptop-preview.css`) или
   сравнение, чтобы в следующий раз её показало локальное сравнение.
6. **Отчёт пользователю.** Коротко: что было, какое правило добавлено, что ещё
   не проверено вживую.

Перед любым новым переносом прочитать таблицу «Taptop facts» в
`system/docs/html-normalizer.md`: это накопленный опыт прошлых импортов. Для переноса из Figma —
ещё `system/docs/figma-extraction.md`; новые уроки извлечения записываются туда.

### Живая проверка после импорта

- Холст редактора на «Компьютер», «Планшет» (768), «Мобильный горизонтальный»
  (480) и «Мобильный портретный» (320): сверить положение и размеры блоков с
  исходником на тех же ширинах.
- Холст прокручивается до конца страницы.
- Индикатор сохранения зелёный; правки через runtime сохраняются только после
  Cmd+S или следующей вставки.
- Опубликованная страница — только с согласия пользователя на публикацию.
- Результат каждой проверки записывается отдельно: `npm run toolkit -- check --project … --artifact … --level editor|published --result passed|failed --note "…"`. Без живой проверки уровень `editor` остаётся `not-recorded`.
